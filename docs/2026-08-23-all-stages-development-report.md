## 3. 关键实现

### 3.1 发布与启动一致性

- `scripts/ensure-backend-package.ps1` 同时检查 Spring Boot 应用入口 class 和 `cfr-0.152.jar`，不再把“文件存在”当作完整包。
- Windows、macOS、Linux 构建入口统一执行版本一致性检查、解包应用冒烟并生成带源码溯源和签名状态的清单。
- 根 `package.json` 是版本唯一修改入口，`scripts/sync-version.js` 同步前端和 Maven `revision`。
- Windows 签名门禁要求 Authenticode 为 `Valid`；未提供证书时只能生成清单为 `NOT_SIGNED` 的内部包。

### 3.2 运行可靠性与诊断

- 第二个 Electron 实例只恢复并聚焦已有窗口，不启动第二个后端。
- 后端使用滚动日志并限制保留量；启动失败信息展示实例 ID 和日志位置。
- `/api/system/diagnostics` 只返回版本、运行环境、最近任务日志和脱敏后端日志，不包含源码、令牌或用户绝对路径。
- 导入、分析、编译、导出任务使用任务 ID 作为操作 ID 写入时间线。

### 3.3 大项目性能

- CFR 按 200 个 class 一批调用主 API，保留任务取消和单文件错误定位。
- 初始文件树只返回固定根节点，展开目录时调用 `/tree/children` 获取直接子项。
- 导出按目录稳定排序并直接写 Zip，不再预先持有全部路径集合。

### 3.4 编码、历史和工作区

- 项目设置提供默认编码，当前文件可以显式选择编码；BOM 优先，显式编码冲突会拒绝。
- 解码和编码均使用严格模式，无法表示的字符不会被问号等替代字符静默覆盖。
- 文件变更记录保存实际编码，搜索和差异使用相同编码合同读取。
- 项目历史可查询分析报告、导出校验和操作时间线。
- 删除历史可以选择保留工作区或先预览清理；未登记的 `.ready` 工作区只能在全局入口中通过快照复验和一次性确认删除。

## 5. 尚需外部条件的正式发布门禁

以下不是通过继续修改业务代码可以真实完成的项目：

1. 将当前开发改动形成用户认可的 Git 提交，再从干净工作区重建，要求清单 `sourceClean: true`。
2. 在持有组织 Authenticode 证书的 Windows 环境执行 `build.ps1 -RequireSigning`，并验证状态为 `Valid`。
3. 在 macOS 原生主机配置 Developer ID 和 notarytool profile，执行签名、公证、staple、原生冒烟和回滚读取验证。
4. 在 Linux 原生主机执行 AppImage/tar.gz 构建、启动验收；渠道要求签名时完成 GPG detached signature 和复验。
5. Electron 页面手工交互按项目约定由用户执行。

在上述门禁全部取得原生证据前，产品定位保持为“Windows 可控内部使用版”，不能改称“跨平台公开发布版”。具体命令、凭据边界和回滚步骤见 `docs/release-runbook.md` 与 `docs/release-checklist.md`。

## 6. 后续版本能力边界

原分析中的 P2-1 Monaco/CodeMirror、P2-2 多版本 JAR 完整编辑映射和 P2-3 业务 JAR 可选重新签名，属于“可作为后续版本的能力增强”，不是五阶段当前完成门槛。当前继续保持以下安全合同：

- 编辑器原文与只读 Unicode 预览分离，不把预览写回原文件。
- 多版本 JAR 明确标记风险，不宣称已经支持每个版本 class 的独立编译写回。
- 修改签名业务包后只允许按明确策略移除失效签名并导出未签名包，不保存密码、令牌或私钥。
